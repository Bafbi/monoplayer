# A refused replay frame is not retried

An attach writes a body's cached state to a newly connected player as one ordered list of frames, once, and [#717](https://github.com/Bafbi/monoplayer/issues/717) made each frame the front leg refused a counted, named thing (`replaySnapshot` in `src/service/monoplayer.js`). [#738](https://github.com/Bafbi/monoplayer/issues/738) asked whether such a frame should be offered again, and the answer is no. That list is written in one synchronous turn, and every cause of a refusal reads state that a socket event, a core call-in, or a frame written earlier in the same list has written. None of the first two can run inside the turn, and the third can only add a refusal, so a second write reaches the same socket with the same bytes and is answered as the first was.

## Considered options

- **Retry once, at the end of the attach stream.** Rejected: the end of the list is the same turn as its start, so the second write is answered exactly as the first was. What it buys is nothing, and what it costs is a reordering for any frame the client would have received between the two writes.
- **Retry immediately, in place.** Rejected for the smaller half of the same reason, and nothing else. It does not reorder, but it cannot be answered differently either. It is the first option minus its one excuse.
- **Fail the attach.** Rejected: `attachPlayer` has no rollback, and the session is `attached` before the first frame is written, so failing means inventing a teardown for a client that is already connected. It also buys nothing for the causes where the client is still there, because the clientbound policy and the client's protocol state are the proxy's own view of a socket it already admitted, and a client that is gone cannot be told why it was kicked.
- **Defer the frame and rewrite it at the end of the turn, outside the list.** Rejected: the frames build a world in order, so a chunk written after the teleport that depends on it is a client standing in a world it has not been sent. The spectator's landing and the reconfiguration flush write an attach stream for the same reason, and neither defers.
- **Retry until the leg takes it.** Rejected: every cause that can accept a second write is one where the state changed, and nothing changes that state inside the turn. A loop is a boot-time hang on the first refusal, in exchange for no frame that a single retry could have delivered.

## Consequences

The client keeps the gap until it attaches again. Every attach replays the same cache, so a refused cached frame is offered again on the next one, which is a retry whose interval is the client's own reconnection rather than the proxy's guess. For the kinds the backend keeps sending, the next such frame overwrites the loss. That is true of chunk data, entity movement and the player list, and false of the join prefix and the registry data, which a server sends once per login, so a refused prefix frame is a client that cannot play.

`refused` counts the frames the client did not get, and it carries two different things: a refusal the leg decided (#717), and a write that threw (#739). It is one number for the causes the leg does not separate, so an operator who needs the cause reads the leg's own counters (`front.policyRefused`, `front.stateRefused` and `front.clientboundSocketClosed`, `docs/telemetry.md`) and its per-client records (`clientboundRefused`, `clientboundStateMismatch`, `configFrameAfterFinish`, `clientboundSocketClosed`), which name the frame, the state and the cause.

Two of those causes cannot reach this counter where it matters. The clientbound policy is a backstop the attach stream cannot trip, because the frame list drops every frame the policy blocks before the list exists (`NOT_REPLAYABLE` in `src/core/clientbound-policy.js`). The wire check only refuses a frame in a lane that runs `wireMode: 'throw'`, which is the rungs and not the deployed lane.

One of them the library reports with no word at all: a socket that can take no bytes. Its writers bare-`return` when the stream under them is not writable, so a frame written there was counted as written and reached nobody (#820). The premise above still holds, because the socket's own state cannot change inside the turn either, so the answer is still no retry, and the leg now refuses that frame in words instead of counting it as written.

The other route was to leave the frame counted and write in `docs/telemetry.md` that `replayed` is an upper bound. That was refused because the socket's state is a fact the leg reads at the write, so an upper bound would be a number an operator has to remember is wrong: the failure #820 is about, kept and documented. What a frame may still not claim is that a client decoded it. A socket that takes the bytes proves the write, not the receipt, and nothing on this side of the connection can see the difference.

`test/service/replay-refused.test.js` holds the decision from the side that costs something. It refuses one frame on its **first** offer only, so a second offer would be taken, and asserts the leg is handed exactly the frames the control attach handed it. A retry that also fails and logs nothing leaves every counter and every line exactly as they are, so the offer list is the only thing that can pin this, and the next attempt to add a retry fails a test instead of passing quietly.
