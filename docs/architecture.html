Executive summary

Build the proven architecture, not a raw packet pipe

The idea is feasible. The core feature already ships in ZenithProxy, a production Minecraft bot proxy that lets whitelisted players log in and control the bot. The correct shape is a stateful semantic MITM: the service terminates the client login, verifies the client with Mojang, holds the puppet's backend session, caches the world state, and synthesizes a fresh join when a client attaches.

The one-sentence recommendation

Run one Node pod that owns a Microsoft-authenticated puppet connection to your backend, accepts your official client through an online-mode front leg with a UUID whitelist, replays the cached configuration and a synthesized join into the live session, and relays play packets with targeted rewrites — never dropping the puppet when the client leaves.

The honest caveat

The architecture is proven, but not in Node. The production proof is Java (ZenithProxy, AGPL-3.0). The Node implementation is the fast, license-clean path, but it is still an implementation bet. That is why the plan starts with a two-day falsifying experiment using a real official client, before product code.

The short answer

What Monoplayer is, precisely

Monoplayer is a client-side proxy with a headless account. It is not a Minecraft server, and it is not a server-side Velocity/Gate proxy. It sits between an official client and a real backend:

Official client→ Monoplayer front leg→ Relay + state cache→ Puppet leg→ Real backend

The puppet is an official Microsoft account logged in headlessly by the service. It is the account the backend sees. The attaching client is another official account, whitelisted by UUID, that proves its identity to Monoplayer and then controls the puppet's body. The client never logs into the backend as the puppet; that would kick the puppet's session.

The service is stateful. The backend TCP session, the world cache, and the puppet's position live in one pod. That is what lets the puppet stay in the world when the client disconnects. It is also the main operational constraint: a pod restart loses the live session and requires a reconnect.

What it is

  • A headless official-account client that stays online.
  • A packet-aware relay that lets a whitelisted official client take control.
  • A bounded state cache that makes late attach look like a fresh vanilla join.
  • A small Kubernetes service with a fast fake-backend test loop.

What it is not

  • A raw byte pipe. Encryption and compression are per-connection.
  • A server-side routing proxy like Deepmine Gate.
  • A bot that plays by itself. The puppet is inert when nobody is attached.
  • A way to share an account with the public or bypass server rules.

What the prior art settles
  • The front leg must terminate encryption with its own RSA key and call Mojang hasJoined.
  • The back leg must authenticate as the puppet with Microsoft device-code auth.
  • The configuration phase must be cached and replayed; it cannot be forwarded to a late client.
  • Play packets can be relayed 1:1 only while attached, same version, with targeted rewrites.
  • The backend session must be owned by the proxy, not the client.
One deliberate difference from ZenithProxy

ZenithProxy lets the attaching player keep their own rendered profile. Monoplayer's design presents the puppet's profile to the attaching client so the client sees the puppet's name and skin. This is protocol-legal — vanilla does not validate Login Success against the client's session profile — but it is not the exact ZenithProxy behavior. The profile is a rendering choice: the backend session is always the puppet, while chat signatures are made by the attaching client and must be stripped or re-signed. Client-side reporting is outside the relay and is not remapped.

Architecture

Two legs, one cache, one live session

The service is a single process with two protocol endpoints and a shared state cache. The front leg is a Minecraft server to the attaching client. The back leg is a Minecraft client to the backend. The relay never passes encrypted bytes between them.

The front leg is a server to the client; the back leg is a client to the backend. The relay decodes, re-frames, and rewrites; it never forwards encrypted bytes.

The front leg (client → Monoplayer)

The front leg uses minecraft-protocol's server half with online-mode: true and encryption enabled. The proxy generates its own RSA keypair, completes the standard Minecraft login, and calls Mojang's hasJoined endpoint. The returned profile is the attaching player's identity. If that UUID is not in the whitelist, the connection is closed during login, before any packet is relayed.

After the whitelist gate, the proxy sends Login Success with the puppet's profile (UUID, name, skin properties). The client believes it is joining as the puppet. This is the subtle part: the client's own account is used only to prove permission to attach; the backend never sees it.

The back leg (Monoplayer → backend)

The back leg is a long-lived createClient connection authenticated with the puppet's Microsoft account. It is established when the pod starts and is owned by the pod, not by any client. It answers the backend's keep-alives and teleport confirms while detached, so the server does not time the session out.

The backend must already whitelist the puppet account, if the server uses a whitelist. That is separate from Monoplayer's own attach whitelist: the backend whitelist says “the puppet may join”; the Monoplayer whitelist says “these clients may control the puppet.”

The state cache

The cache is the product. A late-attaching client has never seen the backend's login or configuration phase, so the proxy must reconstruct a valid current view. The cache is deliberately bounded:

MVP cache trade-off

Applying block updates into cached chunk bytes is the hairiest component and is not demonstrated by the cited projects. The MVP evicts a chunk when a block update touches it, rather than patching its palette — except the chunk under the puppet and its cardinal neighbours, which are pinned. If a pinned chunk is mutated, the proxy patches it or forces a backend resend before attach (a small, server-acknowledged puppet nudge). Without this exception, a single block edit near the puppet could leave the client stuck on “Loading terrain…” forever. Other mutated chunks may be unrendered until the puppet returns; general block-update patching is slice 2.

Session lifecycle

The puppet outlives the client

The service has two independent state machines: the backend session and the client attachment. Client attach/detach changes only the client leg. A backend drop is a session event; a pod restart is a service event.

Reconnect policy

The service never exits because nobody is attached. If the backend drops the puppet, it reconnects immediately with exponential backoff; a player connection is not required to trigger it. A lazy “wait for a player” mode is possible later, but it risks queue position and is not in the MVP.

Hard invariant

Exactly one Monoplayer pod may own a puppet at a time. The Microsoft refresh token is rolling and single-use; a second replica can invalidate it and trigger “logged in from another location” kicks. Use replicas: 1, strategy: Recreate, no HPA, and an alert if the pod count ever exceeds one. This is discipline, not a cluster mechanism: nothing in Kubernetes prevents a second Deployment or a manual scale-up. A future admission guard or leader lock is the mechanical fix if the service graduates.

Late attach

A fresh vanilla join into a session that never ended

The client cannot resume a session it never had. The honest UX is a normal “Loading terrain…” join, typically 1–3 seconds, landing exactly where the puppet is. This is what ZenithProxy ships; it is not a custom attach screen.

Attach sequence

  1. Terminate login. Online-mode handshake, hasJoined, UUID whitelist. Cross-check Login Start against the hasJoined result; deny before relay if not allowed.
  2. Forge Login Success with the puppet's profile: UUID, name, skin properties. This is protocol-legal, but it is Monoplayer's choice, not ZenithProxy's behavior.
  3. Replay cached configuration. Brand, enabled features, registry data, tags, resource-pack state, cookies, finish configuration. Answer the client's Select Known Packs from cache, not by replaying the client's selection. Raw frames, deterministic order.
  4. Synthesize the play join. Login (puppet entity ID), Change Difficulty, abilities, held slot, commands, player-list adds, border, spawn, time, weather, container contents, health, XP, recipes/tags where required, entity events.
  5. Send Game Event 13 (“start waiting for level chunks”). Without it the client stays on “Loading terrain…”.
  6. Synchronize position to the puppet's exact pose with a proxy-owned teleport ID; swallow both Confirm Teleportation and Accept Teleportation from the client.
  7. Set the chunk center and send chunks in fresh Chunk Batch Start/Finished pairs, full radius around the puppet, paced on the client's Chunk Batch Received acknowledgements.
  8. Spawn entities with full metadata, equipment, passengers, and boss bars synthesized as Add first. Then live cutover.
  9. Coalesce state, but queue chat. During the replay, live backend state frames update the cache semantically (absolute poses, metadata patches, chunk evictions); they are not byte-queued. Clientbound chat is the exception: from synthesized Login onward, chat frames must be delivered in order with zero drops or reorders, or the client's global-index chain breaks.
Chat is a stretch goal, not core control

“Strip signatures” is necessary but not sufficient. Serverbound chat also carries a last_seen acknowledgement window tied to that connection's message history. The client's window is not the puppet's window, and vanilla disconnects on a bad window even when enforce-secure-profile=false. The backend also expects the puppet leg to acknowledge messages it receives. A correct implementation needs a per-leg chat state machine: the puppet leg acknowledges and maintains its own window; client chat is re-emitted with the puppet's window, never the client's; clientbound chat is ordered and lossless.

MVP decision: movement, blocks, inventory, and interaction are the core demo. Chat is read-only or blocked unless Gate A proves the per-leg state machine. Re-signing with the puppet's certificates is slice 2. This is a smaller promise than “normal chat,” and it avoids a known kick.

Why not full replay?

Chunks are about 79% of server-to-client bytes and entity deltas about 86% of packet count. A long session would mean gigabytes and minutes of replay. The bounded cache keeps memory in tens of MB and attach latency flat with session age.

Why not reconnect on attach?

Reconnecting as the puppet resets position, inventory, and effects, and on queue servers it can mean hours. It also races “logged in from another location.” It is a failure-recovery path, not the normal attach path.

Packet-level details worth pinning before implementation
  • Login Success must carry the puppet's profile, not the attaching client's. The client's own identity is only the whitelist proof. Vanilla does not validate the profile against the session profile, so this is legal, but it is a Monoplayer choice.
  • Game Event 13 (“start waiting for level chunks”) is mandatory after Login or the client never leaves the loading screen.
  • Set Center Chunk is required so the client centers its chunk view on the puppet, not on 0,0.
  • Chunk batches are one in flight at a time in vanilla behavior; the client acknowledges each batch. Do not blast all chunks without pacing.
  • Boss bars must be synthesized as Add before any live Update, or the client can kick on an unknown UUID.
  • Chat history is never replayed. From synthesized Login onward, live clientbound chat must be delivered in order with zero drops: the client validates a contiguous global_index and its signature cache.
  • Chat acknowledgements are per-connection. The puppet leg must acknowledge backend messages; the client's last_seen window must never be forwarded verbatim.
  • Teleport IDs are per-connection. Backend IDs must not leak to the client, and both client acknowledgements must not reach the backend.
  • Keep-alive is a 30-second deadline. The proxy must answer both legs independently, even during a long attach replay.
  • Cookie requests can arrive in play, not only configuration. Answer from the proxy's cache; never let a fresh client's empty cookie response reach the backend.
  • Pinned chunks: never evict the chunk under the puppet or its cardinal neighbours without a patch or a forced backend resend; otherwise attach can deadlock on “Loading terrain…”.
  • Protocol bump fields: 26.2/776 adds online_mode to play Login and sessionId to Login Success. 26.x treats entity ID 0 as an unassigned sentinel. The 26.1 pin avoids them; the bump task must handle them.
Auth & security

The refresh token is the password

The puppet's Microsoft login uses the device-code flow. The resulting refresh token is rolling, single-use, and valid for up to 90 days of inactivity. It bypasses 2FA for its lifetime. Treat it as the account password.

Short answer

Yes for gameplay: every action the proxy relays reaches the backend on the puppet's connection and is attributed to the puppet. No for client-side cryptography: chat is signed by the attaching client, so the proxy must strip or re-sign it. Reporting stays the client's identity and is out of scope.

Non-negotiables
  • One pod. Two replicas break the rolling refresh token and kick each other.
  • No tokens in git, logs, traces, or images. Redact at the logger and OTel exporter.
  • No public ingress. Tailscale-only data plane; default-deny ingress and egress.
  • Owner-operated only. No selling attach slots, no third-party accounts, no anti-cheat evasion.
  • Your own backend, or explicit permission. Public servers and anti-cheat are the immediate risk.
  • No required resource pack. A client that declines a pack the backend already applied cannot be silently faked into acceptance.
Legal / acceptable-use position

The Microsoft Services Agreement forbids transferring account credentials and makes the owner responsible for all activity. The Minecraft EULA forbids unfair or unreasonable access distribution but permits tools and plugins. An owner-operated, single-account, no-automation proxy stays in the gray zone; enforcement risk is real but unquantified. The clear red lines are handing the account to others, selling access, running other people's puppets, and evading server anti-cheat. The MVP must target only your own server or one that explicitly permits it.

Version strategy

Pin one version. Do not chase Mojang quarterly.

Packet IDs shift every minor release. A proxy that supports “any version” is a translation project, not an MVP. The first slice pins the client, the proxy, and the backend to the same protocol.

This is deliberately one release behind. The library's version support is the constraint, and a pinned backend makes it an ops decision, not a product risk. If your backend is fixed at 26.3, the options are: insert ViaProxy as a translation front (GPL-3.0, extra moving part), or use the Java/MCProtocolLib path (faster protocol currency). The architecture does not change; the substrate does.

Operational rule

A protocol bump is a scheduled maintenance task, not a surprise. Budget 0.5–2 days per quarter: bump minecraft-data, re-run the golden packet logs, fix renames and ID shifts, re-pin the backend. If two consecutive bumps exceed four days, that is a signal to move to MCProtocolLib or accept a ViaProxy front.

Two known bump hazards: 26.2/776 adds online_mode to the play Login packet and sessionId to Login Success; 26.x clients treat entity ID 0 as an unassigned sentinel. The 26.1 pin avoids both, but the bump checklist must name them.

Validation loop

Prove the risky thing first

The plan starts with a two-day experiment that can kill the Node implementation, then a two-week vertical slice. Both live inside the same fast local loop: fake backend, fake client, and no puppet Microsoft account until the final smoke. The attaching client is still a real official client, and the front-leg hasJoined can be stubbed for protocol tests.

Gate A — the 2-day falsifier

This is the smallest test that proves an official client can attach to and drive the puppet's live session. It is throwaway code, not product code.

  1. Use a fake backend with a local hasJoined stub for the go/no-go. A real online-mode backend is optional if you already have the puppet secret; the gate must not depend on it.
  2. Run a minimal Node proxy: online-mode front leg, injected puppet login, cached config, synthesized join, play relay, keep-alive responder.
  3. Attach a real official client. Walk 100 blocks, break and place a block. Run chat as a separate sub-test: first with enforce-secure-profile=false, then with true if cheap.
  4. Disconnect the client. Confirm with an observer bot or server console that the puppet stayed in world for at least 5 minutes.
  5. Reattach. Confirm the client lands on the current state, not a stale snapshot.

Falsified if: the client cannot attach, movement desyncs within the first minute, or reattach is stuck on “Loading terrain…”. If that happens, the pivot is the Java/ZenithProxy path, not more Node code.

Chat failure is a descope signal, not a substrate failure. If the per-leg chat state machine fails, proceed with read-only/blocked chat; do not kill the build on enforce-secure-profile=true alone.

Protocol-level Gate A status

A loopback harness now passes 37/37 assertions: two-leg relay, synthesized play join, current-pose reconstruction, a 5-second attach/detach liveness soak, per-leg keep-alive/teleport/chunk-ack ownership, exactly one backend login, and chat blocked in both directions. See docs/protocol-spike.md and testdata/spike-verdict.md. This is not the official-client gate: encryption, vanilla rendering, online-mode hasJoined, Microsoft auth, secure-chat re-signing, config-phase replay, and the full 5-minute detach window remain unproven. The research, council, and audit trail lives in .scratch/, local only and never in git. The driver-lane plan is docs/driver-lane-plan.html.

Auth gate — the half-day lifeline

The refresh-token write-back loop is a Critical risk and cannot wait for a 90-day surprise. Run this before the live demo:

  1. Device-code bootstrap with the public launcher client ID; record the profile UUID.
  2. Confirm Java ownership via /entitlements/mcstore.
  3. Start the pod, let it refresh, then restart the pod. It must refresh silently, without a new device code, and the replacement token must persist in the Secret.
  4. Run mise run auth:status; it should report token age and last refresh from the Secret timestamp, even if the pod is down.
  5. Verify the backend's prevent-proxy-connections path sees the same egress IP for /join and the TCP connection.

The five L2 invariants

  1. Puppet joins the backend with encryption active.
  2. Client attaches and receives live backend frames.
  3. Client movement reaches the backend as the puppet, exactly once.
  4. Client disconnect leaves the puppet connected.
  5. A second attach receives current state, not a stale replay.

Why this loop is fast

L1 and L2 run in-process on the developer machine with no cluster and no puppet Microsoft account. The slow path (BuildKit, cluster, OpenObserve) only runs after the protocol invariants are green. The live account is the auth gate and final smoke, not the inner loop.

Before the first deploy

  • Puppet account is your own MSA, owns Java Edition, and can join the backend.
  • Device-code bootstrap works; a pod restart refreshes silently; the replacement token persists.
  • No token, UUID, or Secret value exists in git, logs, traces, or images.
  • Secret encryption at rest is verified on Talos, or an external secret store is used.
  • Default-deny ingress and egress are installed; Tailscale is the only data-plane path.
  • Attach gate is online-mode hasJoined + UUID whitelist; denied clients never relay.
  • Replicas are exactly one; pod-count alert exists; attach rate limit and readiness probe are set.
  • Backend is your own or explicitly permits the proxy; prevent-proxy-connections is verified.
  • No required resource pack; chat is read-only/blocked or the per-leg state machine is proven.
  • mise run down rotates/revokes tokens before deleting the namespace.

Kill criteria
  • Gate A fails: official client cannot attach, movement desyncs in the first minute, or reattach is stuck on “Loading terrain…”. A chat-only failure descopes chat; it does not kill the substrate.
  • Slice 1 misses acceptance by week 3: the 60-second demo cannot be produced.
  • Post-demo soak (not part of the three-week demo): first-try attach success <95%, puppet median lifetime <24 h from proxy-caused drops, or a second refresh-token incident within 90 days.
Decision log

The council's calls

Three independent delegates reviewed the same research. All three recommended building the Node semantic MITM; the delivery delegate recorded the strongest dissent (deploy ZenithProxy instead). Confidence is per delegate, not a vote count.

D1

Approach: stateful semantic MITM

Bounded cache + synthesized join + cached config replay. The backend session is never dropped for client lifecycle events. Rejected: full byte replay (unbounded), reconnect-on-attach (loses state), bot-world synthesis (speculative).

Unanimous

D2

Stack: build in Node/TypeScript, don't fork ZenithProxy

minecraft-protocol + prismarine-auth; MCProtocolLib is the fallback. ZenithProxy is the behavioral spec and the fallback deployment. Forking inherits AGPL, Java/Gradle, and 2b2t scope. AGPL only binds distribution, so private deployment remains a legitimate fallback.

3 / 3 recommend build Delivery confidence 78

D3

Version: pin 26.1 / protocol 775

The newest version the Node stack supports. Pin the backend too. No translation layer in slice 1. ViaProxy is the escape hatch; Java is the substrate pivot if currency becomes the bottleneck.

Unanimous

D4

Attach gate: online-mode hasJoined + UUID whitelist

The client proves its own Mojang identity to the proxy; the proxy sends the puppet's profile to the client. Never authenticate the client to the backend as the puppet. Attach token is an optional second factor, not the primary gate.

Unanimous

D5

Late attach: fresh join into the live session

No custom attach screen. The vanilla loading screen is the UX. ~1–3 s, flat with session age. The cache radius is the trade-off.

Unanimous

D6

Validation: Gate A first, then a 2-week slice

Gate A is throwaway and can kill the Node implementation. The slice adds the product surface, L1–L4, and the 60-second demo. The live account is a final manual smoke.

Unanimous

D7

Ops: one pod, one namespace, Tailscale-only, OTLP

Reuse the deepmine loop. Secrets outside git with pod write-back. Default-deny NetworkPolicy. No ArgoCD, no PVC, no HPA for the MVP.

Unanimous

D8

Biggest risk: join synthesis and chat

The synthesized join must be indistinguishable from a fresh vanilla join. If the official client rejects it, the architecture needs a different substrate. Kill criterion is Gate A.

Unanimous

Council dissent, in full

The delivery delegate's strongest counter: “You can have this product this weekend.” ZenithProxy already does everything Monoplayer needs, with more features, on a current protocol, in production. Deploying it is days of configuration; building is roughly three weeks plus a permanent quarterly treadmill. The build is justified only if you value license cleanliness for distribution, a small owned codebase, a Node-native ops loop, and future extension (multi-account, custom control plane) enough to pay for it. If the goal is simply “make it exist for me,” deploy ZenithProxy.

The recommendation is still to build, but Gate A and the three-week cap are there to make the fallback cheap. The product survives a failed build.

What I need from you

Six decisions; four block Gate A

The research answered the mechanism questions. These are values and scope questions that change the plan, so they should be answered by you, not guessed. Q1–Q3 and Q5 gate Gate A; Q4 and Q6 gate the first deploy.

  1. Target backend and version. Is this your own server? Can you pin it to 26.1 / 775, or is it fixed at 26.3 or another version? If it is fixed, we choose ViaProxy or the Java path before writing Node code. Also confirm the puppet account owns Java Edition and can join the backend.
  2. Whitelist. Which Minecraft accounts may attach? Give UUIDs (or usernames we resolve to UUIDs). Is this single-user, a few friends, or a product?
  3. Build vs deploy, and what it is for. Do you want the Node implementation (ownership, license cleanliness, extension) or the fastest path (deploy ZenithProxy as config)? Is the primary use case keeping an account online, remote play, or queue avoidance? That decides how much persistence complexity is earned. The recommendation is build, with Gate A and a three-week cap.
  4. Pod restart semantics. Is it acceptable that a pod restart drops the live backend session and reconnects (position/inventory may reset depending on the server)? Persisting a live TCP session across restarts is not in the MVP.
  5. Chat. Is the backend's enforce-secure-profile off? Even if it is, outgoing chat needs a per-leg last_seen state machine. Is read-only/blocked chat acceptable for the demo, or is chat a must-have? If it is a must-have, Gate A must prove the full state machine, not just signature stripping.
  6. Exposure and scope. Confirm Tailscale-only, owner-operated, own-server use. If you need public ingress or third-party users, the security and legal design changes materially.
Recommended next action

Answer 1–3 and 5, then run Gate A. Do not build the product slice until an official client has attached to a live puppet and reattached after a disconnect. Answer 4 and 6 before the first deploy.
