Executive summary

Gate B is a testbed, not a feature

Gate A proved the relay mechanics with protocol clients. Gate B must prove the thing a player will actually do: an official 26.1.2 client, with a real Microsoft session, attaches through Monoplayer, renders the puppet's world, controls it, detaches, and reattaches without a second backend login.

The recommendation in one paragraph

Put the official client on nath with Prism 11.0.3 (11.1.1 is current) and a thin client-only Fabric driver. Because the real target is Paper behind a proxy, make Monoplayer → Toxiproxy → Velocity → Paper 26.1.2 the pass path; the direct Paper client row is only the G0 host baseline. Keep Vanilla 26.1.2 direct as reference parity and the Fabric server as a required compatibility report. Require an unmodded Prism run as the anti-masking witness. Keep the decompiled-source workflow outside the gate. The gate is a one-to-two-week verdict, with a separate hardening tail.

What changed since Gate A

Gate A passed 37/37 on loopback. It did not exercise encryption, online-mode hasJoined, Microsoft auth, secure chat, config-phase replay, or a real client. Gate B is where those become falsifiable. The biggest product risk is no longer the relay; it is whether a real client accepts the synthesized configuration and join on a real backend.

The pass claim

One sentence, no ambiguity

Gate B passes when an official Minecraft Java 26.1.2 client, launched from Prism with a real Microsoft session, joins Monoplayer's online-mode=true front leg, is admitted by real hasJoined and the UUID attach whitelist, controls the puppet through join → render → move → break → place → 5-minute detach → reattach at current pose against a real Paper 26.1.2 server behind Velocity, with exactly one backend login across the attach/detach cycle (fault rows may have one deliberate reconnect, total two, never a loop), the player UUID never reaching the backend or proxy as a separate player, and a non-whitelisted account denied before Login Success; the core scenario is also observed once with an unmodded client, and every claim is backed by client state, independent server/proxy state, and a visual artifact.

What the sentence deliberately excludes

  • Chat, resource packs, and secure-chat re-signing.
  • Multiple simultaneous clients or multi-account pooling.
  • 26.2/26.3, ViaProxy, Bedrock, and version translation.
  • Production deployment and public ingress.
  • Fabric results as gate-blocking claims.

What cannot be descoped

  • The official client, not a protocol bot.
  • Online-mode hasJoined on the front leg.
  • Two distinct accounts and two separate whitelists.
  • Exactly one backend login across attach/detach.
  • Five-minute detach and current-pose reattach.
  • The unmodded witness.
Topology

Client on nath, backend on the cluster

The split is now real: Prism and the official client stay on the laptop; the backend, Monoplayer, and Toxiproxy live in monoplayer-gate-b. The cluster is on the same LAN, and Tailscale currently routes directly, so the path is acceptable for Gate B. Record the route and latency in every report.

The client stays on nath; the cluster holds the backend and, later, Monoplayer and Toxiproxy. A server-side proxy, if used, goes behind Monoplayer, never in front.

Why this split works

The laptop has the GPU, display, and Prism; the cluster has the CPU, memory, and stable backend lifecycle. The cluster is on the same LAN and Tailscale currently routes directly, so the extra hop is acceptable for the first real-client gate. Record the route; do not pretend it is loopback.

Measurement note

Every report must record the client host, the backend node, the Tailscale path (direct vs relay), and the measured attach time. If the path relays or the LAN becomes noisy, the fault-latency rows are the first ones to distrust.

Client control

The driver is the instrument. The unmodded run is the witness.

A process being alive is not a pass. Gate B needs to know the client left DownloadingTerrainScreen, has a level and player, rendered chunks, aimed at a real block, and sent a vanilla interaction. That is a client-state assertion, not a screenshot.

The driver contract

A client-only Fabric mod. Loader only; no Fabric API; no mixins into Connection, ClientLoginNetworkHandler, ClientPlayNetworkHandler, packet codecs, or Netty. It binds 127.0.0.1:25599 with a per-run token and exposes newline-delimited JSON: status, look, move, break, place, disconnect, reconnect, screenshot, quit.

It reads Minecraft.getInstance() and calls the vanilla interaction path for block edits. It does not receive, log, or store the player's access token. Every assertion records clientLane: driver | unmodded | offline-precheck.

Anti-masking rule

The driver is a mod, so it can mask a vanilla bug. One unmodded Prism run is mandatory. If the driver passes and the unmodded run fails, the gate is blocked, not passed. If the driver fails and the unmodded run passes, the driver is broken; fix it or demote it, do not average the results.

Why not xdotool as the primary?

xdotool sends XTEST events to the focused window. Minecraft's GLFW window can lose focus, the pointer is grabbed in-game, mouse-look is relative, and the loading/disconnect screens change what a click means. Synthetic XSendEvent is often ignored by GLFW. The result is a runner that fails on window-manager timing, not on Monoplayer. xdotool is the unmodded witness fallback, not the primary instrument.

Faults belong on the puppet leg

A fault on the client leg tests the client's tolerance. A fault on the puppet leg tests Monoplayer's session ownership. Gate B cares about the latter.

Hard rule

A server-side proxy goes behind Monoplayer, on the puppet leg. In front, it terminates the player's login before Monoplayer's hasJoined, which makes the attach whitelist meaningless. A proxy in front is a configuration error, not a variant.

Why not a chaos framework or tc netem first?

Toxiproxy is a single static binary with an HTTP API and deterministic toxics. It keeps the fault schedule in the scenario log and needs no root. tc netem is the optional kernel-realism check: root-only, interface-wide, and harder to make per-flow. Add it later if you need qdisc realism, not for the first gate.

Two accounts

The backend sees the puppet. The front leg sees the player.

Gate B needs two distinct, owner-operated Microsoft accounts. One account cannot prove identity separation: the same UUID on both sides masks the exact failure the gate exists to catch.

Puppet

  • Dedicated alt; headless only; never in Prism.
  • Device-code bootstrap, then rolling refresh token in .secrets/puppet/.
  • One writer: the proxy. auth:status is read-only; --refresh needs a lock.
  • Backend whitelist contains the puppet only.
  • Owns Java Edition and has multiplayer enabled.

Player

  • Your normal account; added to Prism only.
  • Never logs into the backend; only the front leg.
  • Attach whitelist contains the player only.
  • Prism stores tokens in plaintext today; keep the root private and disk-encrypted.
  • One Prism instance per account; no duplicate GUI puppet.

The user flow

  1. Verify both accounts: Java ownership, profile UUID, multiplayer privilege, 2FA, Xbox profile.
  2. Bootstrap the puppet: mise run auth:device-code --account puppet; approve in a browser/phone within 15 minutes.
  3. Sign into Prism with the player account only; create the 26.1.2 instance; pin the account.
  4. Add the two whitelists: backend = puppet UUID; attach = player UUID. Never merge them.
  5. Run the gate: Prism joins 127.0.0.1:25565; the scenario drives the rest.
  6. Review evidence: screenshots, report JSON, redacted logs.
Duplicate-session rules
  • One proxy process, one replica, one token writer. Two refresh loops race the rolling token.
  • Never run a GUI client as the puppet while the proxy is live.
  • Never point the player at the backend directly.
  • A one-account run is a labelled smoke (twoAccount=false), never a Gate B pass.
Token boundary

The refresh token is the password. It lives only in .secrets/ (local Gate B) or the untracked monoplayer-puppet-auth Secret (later deploy). Pass the cache path, never the token. No token, device code, or real account identifier in git, logs, traces, images, or artifacts. Gate B v1 uses local custody; cluster custody waits until Talos secret-at-rest is verified.

Decompiled source

A recipe, not a gate criterion

26.1 is unobfuscated. minecraft-data already has protocol 775, and javap can answer packet-registration questions without a decompiler. Decompiled source is an engineering convenience for implementation details, not a Gate B acceptance criterion.

Recommended workflow

  • Tiny Loom project in tools/mc-source/: Loom 1.19.3, Gradle 9.8.2, Java 25.0.2.
  • Minecraft 26.1.2 (match the client), no mappings line.
  • genSourcesWithVineflower; Vineflower 1.12.0.
  • Output only in .cache/minecraft/26.1.2/; .cache/ gitignored.
  • Commit the recipe; never the output, jars, or CI artifacts.

Order of reference

  1. minecraft-data protocol JSON.
  2. minecraft-protocol source.
  3. javap -c -p on the pinned client jar.
  4. Vineflower/decompiled source only for validation, ordering, or behavior the JSON cannot express.
Legal boundary

Decompiled Minecraft code is Mojang's copyrighted code. Removing obfuscation did not relicense it. Local inspection on a licensed machine is the intended modding use; committing, publishing, shipping, or attaching the source or jars is redistribution. Commit the recipe, not the output. This is not legal advice.

Fatal anomalies

  • Stuck on “Loading terrain…” or in configuration past 120 s after the plain-server baseline passed.
  • A second backend login caused by attach/detach on a no-fault row, or more than one reconnect on F4/F5.
  • Movement or a block edit reaching the backend zero times or twice.
  • The backend ever seeing the player's UUID or name.
  • A detached world mutation not visible after reattach.
  • Any token, refresh token, device code, or RCON password in logs or artifacts.
  • Driver passes / unmodded witness fails.

Explicit descopes

  • Fabric not gate-blocking.
  • Chat blocked/read-only; no re-signing.
  • No resource packs, multi-client, or 60-minute soak.
  • No performance benchmark.
  • No cluster token custody.
  • No decompiled source in Gate B.
Kill criteria
  • Host: G0 not 2/2 within 3 working days → stop; fix/replace the client lane. Gate blocked, not failed.
  • Driver: cannot build against 26.1.2 within 2 days → switch primary to unmodded + xdotool, accept manual block-edit checks, lower the claim.
  • Product: B1 cannot get a real 26.1.2 client to a null screen with rendered chunks after a bounded 2-day config-replay fix → treat the synthesized-join path as failed and escalate the substrate pivot.

Decision log

The council's calls, and the dissent

D1

Client: Prism + driver as instrument, unmodded run as witness

The driver is the only practical way to assert screen == null, level/player, rendered chunks, hit result, and block state. The unmodded run is the only way to detect masking. Both are mandatory; neither alone is a pass.

Resolved Auth council wanted unmodded primary

D2

Backends: Paper behind Velocity is the pass path; Vanilla parity; Fabric compatibility

The real target is Paper behind a proxy, so Velocity is core. Paper direct is the G0 host baseline; Vanilla is reference parity. Fabric is required to report, but a Fabric failure is a compatibility finding unless the product claims modded servers.

Resolved Testbed architect wanted Fabric mandatory

D3

Network: Toxiproxy on the puppet leg; any proxy behind Monoplayer

Faulting the client leg tests the client. Faulting the puppet leg tests Monoplayer's session ownership. A proxy in front would terminate the player's login and make the attach whitelist meaningless.

Unanimous

D4

Accounts: two owner-operated MSAs, local custody for v1

Puppet headless only; player in Prism only; backend whitelist = puppet; attach whitelist = player; one writer; one replica. Cluster Secret custody is deferred until Talos secret-at-rest is verified.

Unanimous

D5

Decompiled source: recipe, not gate

26.1 is unobfuscated; minecraft-data and javap answer most questions. If needed, Loom/Vineflower to .cache/26.1.2, never committed. It cannot falsify a Gate B claim.

Unanimous

D6

Gate: one-to-two-week verdict, host-first, numeric kill rules

The gate is blocked if the host or second account is missing. The instrument is the top risk. The product kill is config replay on the first real row, not chat or Fabric.

Resolved

Strongest dissent

The auth/security council argued that an unmodded client is the only true evidence and the Fabric driver should be a debugging aid, not a mandatory instrument. The testbed and delivery councils argued the driver is mandatory because the alternatives cannot assert block edits and rendered chunks reliably. The synthesis keeps both: driver for precision, unmodded for anti-masking. If the two disagree, the gate is blocked.

The second dissent is Fabric. The testbed architect wanted Fabric mandatory because it is cheap; the delivery owner deferred it because it is a compatibility claim, not a core promise. This plan requires the Fabric run and reports it, but does not let it block the core verdict unless the product claims modded servers.
