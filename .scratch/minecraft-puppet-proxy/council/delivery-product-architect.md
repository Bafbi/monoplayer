# Monoplayer — Council Decision Memo

**Council role:** delivery-product-architect
**Lens:** delivery risk, product scope, schedule and maintenance honesty
**Date:** 2026-11-05
**Inputs:** `map.md`, research notes 01 (protocol/auth/prior art), 02 (late attach), 03 (runtime/validation), 04 (security/legal/ops)

---

## 1. Recommended architecture

Monoplayer should be a **single-pod Node/TypeScript service** built on `node-minecraft-protocol` + `prismarine-auth`, implementing the **stateful semantic MITM** proven by ZenithProxy: the pod owns one long-lived, Microsoft-authenticated connection to the operator's own backend as the puppet; whitelisted official clients attach over Tailscale to a second leg terminated with our own RSA keypair, prove identity via Mojang `hasJoined` against a UUID whitelist, receive a synthesized Login Success carrying the puppet's profile, a replayed cached configuration phase, and a synthesized play join from a bounded state cache (raw chunk frames; coalesced entity, inventory, tablist, scoreboard, boss-bar, time/weather state), then drive the puppet through play-packet relay with keep-alive/teleport/chat hygiene — and the backend session survives every attach/detach cycle (note 02 §4 invariant). Both legs are pinned to one protocol version, no translation. Delivery path: a **2-day throwaway falsifying experiment** (note 01 §8, note 02 §7.6) as a gate, then a **2-week product slice** through the proven deepmine mise → BuildKit → zot → Kubernetes loop with OTLP to OpenObserve, then a manual smoke with a real Microsoft account secret. **ZenithProxy is the spec and the escape hatch, not the build target** — if the build falsifies, deploying it as configuration still delivers the product.

## 3. Explicitly not in the MVP

- **No translation layer** (no ViaVersion/ViaProxy on either leg): both legs pinned to D3's version.
- **No spectators, no multi-attach, no multi-account pooling**, no quotas/billing (map.md).
- **No bot behavior or automation**: no Mineflayer physics, no pathfinding, no auto-eat, no AFK movement — the puppet is inert when unattended; the proxy only answers keep-alives/teleport confirms (02 §3.4). Automation would also cross the ToS line (04 §3).
- **No secure-chat re-signing**: MVP targets a backend with `enforce-secure-profile=false`; client chat is relayed unsigned (strip signatures). Re-signing with the puppet's certificates is slice 2+ (01 §2, §5).
- **No section-aware chunk mutation**: block changes evict affected chunks from the cache (always correct, zero palette surgery). Consequence, stated honestly in the README and demo script: after a long detach with world edits nearby, re-attached client sees modified areas unrendered until the puppet re-enters render distance. Single-block `Block Update` application is slice 2; `Section Blocks Update`/`Multi Block Change` mutation later. (This is the component no cited project demonstrates — 02 §6, §7b — so it is the most honest MVP cut available.)
- **No transfer support** beyond block-and-reconnect; no re-entry to CONFIGURATION mid-play; no modded servers/registries (02 §6, map.md).
- **No dashboard, IdP, or end-user identity provider**; no public ingress; no ArgoCD, PVCs, or HPA; no Bedrock (map.md).
- **Nothing** that evades server anti-cheat, bans, or access controls (map.md, 04 §3).

## 4. Smallest demo, schedule, and the 2-day vs 2-week question

**The demo is the acceptance script in D6, nothing more and nothing less:** an official client, on a second machine, attaches to the operator's own live server through Monoplayer, plays, detaches, and reattaches. Everything in §3 is deliberately absent so the demo cannot grow scope.

Schedule, one engineer, honestly estimated:

| Phase | Effort | Output |
|---|---|---|
| Gate A: falsifying experiment (throwaway) | 2 days | Go/no-go on the Node stack at the pinned protocol |
| Slice 1: product repo + cache + relay + whitelist + L1/L2 fixtures | 7 days | All five L2 scenarios green locally, golden baseline captured |
| Slice 1: mise/BuildKit/deploy + L3 + NetworkPolicy/secrets + OTel | 4 days | `monoplayer-dev` running, signals in OpenObserve |
| L4 smoke: real Microsoft account + real backend + official client | 1 day | The demo video; accept or exit |
| **Total to demo** | **~3 weeks** | |
| Recurring: quarterly version bump (minecraft-data bump, re-run goldens, fix renames/ID shifts, pin backend) | 0.5–2 days/quarter | Treat >4 days as the D8(c) exit signal |

The 2-day vs 2-week question resolves as: **both, in sequence, as gates** — Gate A protects the slice, the slice turns Gate A into a product. Skipping A is the classic delivery error here; skipping the slice leaves you with a proof and no product.

Maintenance burden, stated plainly: Monoplayer is not "build once, run forever." It is a small product with a permanent quarterly treadmill (Mojang ships quarterly now — 03 §evidence) plus the version-lag exposure of a small maintainer org. The MVP must be scoped as if maintenance is a first-class feature, which is why D2 prefers a small owned codebase over a large fork, D3 pins versions, and D8 budgets the bump.

## 5. Strongest argument against this recommendation

**You can have this product this weekend.** ZenithProxy — GraalVM native, <300 MB RAM, device-code auth, secure whitelist via `hasJoined`, spectator mode, persistence across disconnects, ViaVersion currency through 1.21.11 and beyond (01 §4, §5) — *is* Monoplayer's MVP plus features, in production on 2b2t for years. Deploying it on the homelab is days of config, not weeks of code. My recommendation spends ~3 weeks re-deriving a shipping feature in an ecosystem that lags Mojang by a release, to end up with less functionality and a maintenance burden we own instead of one the ZenithProxy community owns. The only things building buys — license comfort (irrelevant for private self-hosting, since AGPL binds distribution, not personal use), language fit with the homelab, and a codebase small enough to extend — may not be worth three weeks and a permanent treadmill. If the goal is "I want this to exist for me," fork-and-configure wins on every pure delivery metric.

I still recommend building, because: Monoplayer's scope is ~10% of ZenithProxy's, the map's product questions point at features ZenithProxy will never have (clean seams, multi-account later, first-party ops), AGPL would bind any future distribution, Java ops is this homelab's worst-fitting loop (03 table), and the Node stack's in-process fixtures are the only cheap path to the validation depth the map demands. But the counter is strong enough that my confidence is 78, not 90 — and it is why D8's fallback is "deploy ZenithProxy and call the product done," not "rebuild in Java."

## 6. What evidence would change my mind

1. **Gate A falsified on modern protocol** (official client kicked for chat/session verification, stuck on "Loading terrain", or movement desync within a minute on a real online-mode backend) → kill the Node build; deploy ZenithProxy-as-config; re-scope Monoplayer as our ops/control plane around it.
2. **ZenithProxy-as-config covers the whole MVP value in under a day with acceptable UX** — I would run this in parallel with slice 1 anyway as the reference UX baseline; if it makes slice 1 look like re-derivation, the product re-scopes and our build investment shrinks to a thin wrapper.
3. **Version currency becomes non-negotiable** — e.g. the backend must be someone else's always-current server (friends' realms, public networks), or `minecraft-data` is more than one release behind at a slice start → the Node stack fails its one soft spot and the pivot is MCProtocolLib or a ViaProxy front (03 §risks).
4. **`enforce-secure-profile` proves unavoidable** on the real target backend and re-signing proves hard → chat descopes to block/read-only, or the whole build path is questioned.
5. **PrismarineJS stalls for a full release cycle** (bus factor, 03 §costs) → same Java pivot, before we own more handler code.

## 7. Confidence

**78 / 100.**

High because: the exact feature ships in three independent implementations (02 §7b), both protocol halves and auth are first-party in one library (03), and the ops loop is copied, not invented (03/04). Not higher because: client tolerance of our exact synthesized-join packet order at the pinned protocol is explicitly speculative (02 §7b), the chunk-mutation component is deferred by MVP cut rather than solved, the version treadmill and maintainer bus factor are real recurring costs, and the build-vs-fork question is genuinely close (it is answered by product intent, not by engineering facts).
