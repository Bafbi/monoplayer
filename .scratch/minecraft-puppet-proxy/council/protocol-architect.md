# Council memo — protocol-architect: Monoplayer data plane

**Role:** protocol-architect (protocol correctness, data-plane architecture)
**Date:** 2026-11-05
**Inputs:** map.md; research notes 01, 02, 03, 04

## 1. Recommended architecture (one paragraph)

Monoplayer's MVP is a **stateful semantic MITM in Node.js** — one pod, two sockets, one pinned protocol (Java **26.1 / protocol 775** on both legs, no translation layer). The **puppet leg** is a long-lived online-mode client owned by the proxy (`minecraft-protocol` `createClient` + `prismarine-auth` Microsoft device-code auth with rolling refresh); while no client is attached the proxy answers the backend's keep-alives, teleport confirms, cookie requests and chunk-batch acks itself, so the server-side session never drops for any client lifecycle event. The **client leg** is an online-mode server half (`createServer`) with the proxy's own RSA keypair: the attaching official client completes the standard encrypted handshake, the proxy calls Mojang `hasJoined` to prove the attaching player's own identity against a UUID whitelist, then forges **Login Success with the puppet's profile** (UUID/name/textures) and replays the cached configuration phase (raw frames) followed by a **synthesized play join** built from a bounded state cache (Join Game fields incl. the puppet's backend entity ID, LRU chunk bytes, entity registry, player list, inventory, time/weather); play packets then relay with targeted rewrites — entity IDs pass through verbatim (single controlling client), keep-alive and teleport IDs are owned per leg and never bridge, chat is stripped to unsigned (re-signing with the puppet's certificates is the documented upgrade), and the client's movement is the single position loop driving the puppet. This is ZenithProxy's proven architecture re-implemented on an MIT/BSD stack to stay clear of AGPL.

## 3. Strongest argument against my recommendation

The two riskiest correctness components — a vanilla client tolerating our exact synthesized join order on protocol 775, and keeping the cache coherent with live backend block updates — are **demonstrated nowhere in the Node ecosystem**. The only production proof of the whole pattern is ZenithProxy itself, in Java, at 1.21.4 with ViaVersion (01 §4). Forking ZenithProxy (AGPL) or building directly on MCProtocolLib (MIT, GeyserMC's same-day protocol currency) buys a proven data plane and eliminates the version-lag argument, at the cost of gradle/JVM iteration speed and — for the fork — AGPL-3.0 covering the whole service. My stack choice also ships the MVP one release behind Mojang (26.1 vs current 26.3) on day one, which is only acceptable because the backend is pinned with it; if the target server ever can't be pinned, the version decision collapses and pulls D2/D3 down with it.

## 4. What evidence would change my mind

1. **02 §7.6 fails with the real vanilla client** (stuck on "Loading terrain…" or kicked within 60 s of the synthesized join) → abandon the Node substrate; re-implement the identical architecture on MCProtocolLib (MIT), or fork ZenithProxy if AGPL is acceptable.
2. **`minecraft-data` 775 mis-expresses any packet we depend on** (registries, cookies, Login fields, chat session data) in a way that can't be patched upstream quickly → Java stack.
3. **Chunk-byte mutation benchmarks show JS cannot keep up** with realistic backend block-update rates (frame loss → client desync) → Java, or accept a permanently reduced cache-coherence contract.
4. **`prismarine-auth`'s public-launcher-client-ID device-code path 403s, or silent refresh fails inside 90 days** (04 exp. 1) → MCProtocolLib + MinecraftAuth, since DIY MSA→XBL→XSTS auth is a maintenance trap (03).
5. **The operator's target backend cannot be pinned to 26.1** (e.g. it is a third-party server on 26.3+) → insert a ViaProxy front (accepting GPL-3.0 and the translation-hop complexity) or move to the Java stack, whichever measures cheaper.
6. **The live 01 §8 experiment shows duplicate-login kicks or the puppet dropping on attach** despite single-session ownership → the "one pod, two sockets, one live session" topology itself is wrong; revisit 02 §3.3 warm-reconnect semantics.

## 5. Confidence

**80/100.** The architecture (semantic MITM, bounded cache, synthesized join, forged puppet profile) is proven by three shipping projects (01 §4, 02 §7b) and the protocol mechanics (hasJoined crypto, config/play state machines, keep-alive deadlines, entity-ID semantics) are documented and stable in the pinned version. The deduction is for execution risk: join-synthesis tolerance by the official client on 775, chunk-cache coherence, and the Node ecosystem's version currency are each real unknowns that the ordered falsifiers (03 invariants → 02 §7.6 → 01 §8) are specifically designed to surface within the first two weeks.
