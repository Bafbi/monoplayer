# Council memo — reliability-security-architect

**Date:** 2026-11-05
**Lens:** reliability, security, Kubernetes operations
**Read:** map.md; research 01 (protocol/auth/prior art), 02 (late attach), 03 (runtime/validation), 04 (security/legal/ops)

## 1. Recommended architecture (one paragraph)

Run a **stateful semantic MITM as a single-replica Kubernetes pod that we treat as a pet, not cattle**: one Node/TypeScript process holding two sockets — a `createServer` online-mode front leg that proves the attaching client's identity via `hasJoined` against a UUID whitelist, and a `createClient` Microsoft-authenticated puppet leg owned by the pod and never dropped for client lifecycle events (01 §7, 02 §4.3). The pod maintains the bounded state cache (config frames, raw chunk bytes, entity/inventory/tablist snapshots) and serves late attaches by replaying cached config + synthesizing the Join Game with semantic buffering of live deltas (02 §4). The MSA refresh token lives only in an untracked, namespaced Secret with encryption at rest and RBAC scoped to this workload, and — because refreshes are single-use and rolling (04 §1) — the pod writes each replacement token back to the Secret itself, under a hard invariant that **two pods never run concurrently** (Deployment `replicas:1`, `strategy: Recreate`, no HPA). The attach port is exposed only via a Tailscale `LoadBalancer`; ingress is default-deny (peers: own namespace + tailscale) and egress is default-deny allowlisted to DNS, the four Microsoft/Mojang hosts, the backend server, the in-cluster registry, the OTel collector, and the Kubernetes API (04 §5, plus the two endpoints 04's egress list misses). OTLP flows to the existing OpenObserve stack; deploys flow through the proven deepmine loop (mise → in-cluster BuildKit → zot → `monoplayer-dev`); correctness is proven by the L1–L4 test pyramid (03) and gated by the §7.6 falsifying experiment with a real official client **before** any product code is built (02 §7.6).

## 3. Strongest argument against my recommendation

The architecture demands that a **live TCP session with irreplaceable world state live inside exactly one pod's memory**, while everything else in this homelab is cattle-style and ArgoCD-managed. Kubernetes is structurally hostile to this: any node reboot, OOM-kill, image rollout, drain, or manual `kubectl scale` destroys the session and all progress in it; the refresh token's single-use rolling semantics mean the one mistake K8s makes easiest — running two replicas — doesn't just corrupt state, it bricks the account's login (two pods would also fight each other with "logged in from another location" kicks, MC-172541/PaperMC#5303, 02 §1). The mitigation stack (Recreate, no HPA, RBAC write-back, pod-count alerts, preStop drains) is all convention and discipline, not mechanism — nothing in the cluster *prevents* `replicas:2`. A stateless per-attach design would be dramatically more K8s-native and operationally boring; we are paying that cost for session persistence, which is exactly the feature the research shows only this shape can deliver (02 §3.3 rejects reconnect-per-attach for good reasons). If persistence matters less to the operator than we assume, this complexity is unearned.

## 4. What evidence would change my mind

1. **§7.6 fails** (official client never leaves "Loading terrain…" or kicks within 60 s of a synthesized join) → the MITM is falsified; pivot to a ZenithProxy fork (architecture transfers 1:1, 01 §7) or drop the project.
2. **04 §8(1) fails** — silent refresh doesn't work with the public client ID or inside the 90-day window → auth strategy is falsified; go the mce-reviewappid route or stop.
3. **The two-pod invariant proves unenforceable in practice** (we catch a second replica or a token race in the wild) → strengthen with an admission policy or leader-election guard before any wider deployment.
4. **L3 soak shows the puppet session can't survive unattended windows** (keep-alive or egress flakiness the proxy can't fix) with median lifetime < 24 h → session ownership model is wrong; re-examine warm-reconnect frequency (02 §3.5).
5. **`minecraft-data` ships 26.3 support quickly and pinned-client friction (operators must run 26.1) turns out to be the dominant pain** → re-pin immediately; if the Node stack can't keep within one release of current by habit, the Java fallback becomes the primary stack (03 risks).
6. **Policy change:** Mojang/Microsoft starts rate-limiting or banning device-code headless logins, or a target server flags proxied sessions → stop, this project is not viable as designed.

## 5. Confidence

**80 / 100.** The security posture (04) and the ops loop (03) are proven by direct reuse; the attach/keep-alive/single-leg mechanics are proven by three shipping projects (02 §7b). The 20 points of doubt sit exactly where the research itself is honest: the synthesized-join packet order on our pinned version, block-change mutation of cached chunk bytes, and secure-chat behavior are extrapolated, not demonstrated (02 §7b) — and my whole recommendation's viability hangs on those three plus a token lifecycle that survives pod restarts. That is precisely why the falsifying experiments run before product code and why the kill criteria are numeric.
