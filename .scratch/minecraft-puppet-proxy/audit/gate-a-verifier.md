## Verdict

**PASS WITH CAVEATS** as the runbook's narrow *protocol-level relay spike*.
**FAIL as the architecture's Gate A / L2 validation loop** as written in `docs/architecture.html` (§Validation loop, "the five L2 invariants").

The mechanics that are tested are real, not mocked in the middle: a live two-leg proxy moves decoded frames between a real `minecraft-protocol` client and server on loopback, keeps one backend login, and replays a cache to a second client. That is worth keeping.

But the harness does **not** prove several things the runbook says it proves, and one claim is demonstrably false:

1. **Reattach does not land where the puppet actually is after client movement.** The proxy caches only serverbound? No — only *clientbound* frames. It forwards the attaching client's movement to the backend but never records it. A client that walks to `2.5` and detaches reattaches at the last backend-sent position, `0.5`. Falsified by probe `position-reattach-probe.mjs`.
2. **A client kicked immediately after the join still passes the test.** The fake client records `received.ended`, but no assertion ever checks it; all error logs are sent to `logStream: null`; the scenario samples state only at `ready()` and never holds the connection. The Gate A requirement is "stays connected"; the harness does not test staying connected at all.
3. **Clientbound chat is cached and replayed**, contrary to the architecture's "chat history is never replayed" and the auditor's P0-2. A `player_chat` sent by the backend lands in `cache.window` (probe: `cacheNames()` includes `player_chat`) and will be replayed to the next client with a stale `globalIndex`/signature cache. The runbook's "chat is blocked" is true only for serverbound `chat_message`.
4. **The "bounded" cache is unbounded before the join completes.** If the backend never sends `chunk_batch_finished`, every play frame accumulates in `cache.prefix` (probe: 2002 frames, `boundedBy512: false`). The test's `framesCached <= 512 + 16` is vacuous at 8 frames and does not test this path.
5. **Per-leg ownership is correct in the implementation, but almost none of it is asserted by the harness.** My probes confirm backend keep-alives, teleport confirms, chunk acks, and front keep-alives work — but the shipped test never exercises or checks them because the fake client sends no `teleport_confirm`/`chunk_batch_received` and the run is under one second.

The runbook is honest about the biggest external unknown (official vanilla client, `hasJoined`, Microsoft auth, secure-chat re-signing, config replay). It is **not** honest about items 1–4, about encryption, or about the fact that the front leg's configuration is generated by the front library rather than replayed from the backend.

**Self-count assertions** (the metric is incremented in the same code path the assertion checks):

## 2. Is the raw-frame cache/replay legitimate for a late attach at the same protocol version?

At the same version, **re-framing a decoded frame is legitimate**; per-connection compression/encryption makes byte relay illegal, and `writeRaw` re-frames correctly (wire tap confirms compressed, zlib-valid front-leg frames). The question is which cached frames are *per-connection* and which are *absolute state*.

| Cached frame | Legality at 775 | Per-connection state? | Verdict |
|---|---|---|---|
| `login` (play) | Valid world/session fields; `entityId` reused intentionally | `entityId` is per-connection but intentionally identical to the puppet's | **OK** |
| `game_state_change` (13) | World state | No | **OK** |
| `position` | Valid frame, but it is the *backend's* teleport ID and an *old absolute pose* | `teleportId` is per-connection; the pose is stale after client movement | **NOT OK**: stale pose (P0-1) and backend IDs leak to the client. The proxy drops the client's confirm, so the backend is not corrupted today, but this violates the architecture's "proxy-owned IDs" and is wrong if the client's behavior changes. |
| `chunk_batch_start` / `chunk_batch_finished` | Framing is replayable; the client accepts it | Batch state is per-connection | **OK for a protocol client**, but not vanilla-paced: the proxy sends the whole cache synchronously and drops the client's `chunk_batch_received`. |
| `map_chunk` | Valid chunk bytes; probe confirms `(0,0)` grass, empty heightmaps, no block entities | Chunk data is world state | **OK at 775**; the client may need neighbors/heightmaps for full vanilla rendering (unproven). |
| `block_change`, `multi_block_change`, etc. | Valid, replayed chronologically after the chunk | World state | **OK in this scenario**; the product must coalesce into chunk bytes (known gap). |
| `player_chat`, `profileless_chat`, `hide_message` | **Cached like any other frame** | `globalIndex`, signature cache, last-seen window are per-connection | **NOT OK** — probe shows `player_chat` cached; next attach replays it. Violates research 02 §4.2.6 and auditor P0-2. |
| `cookie_request`, `add_resource_pack`, `ping`, `transfer`, `start_configuration`, `kick_disconnect` | Cached raw; front responses not filtered (`cookie_response`, `resource_pack_receive`, `pong` are not in `DROP_SERVERBOUND`) | Per-connection or terminal | **Untested and likely wrong**: a replayed cookie request can leak the fresh client's empty cookie response to the backend; a replayed resource pack push can duplicate a status; `start_configuration`/`transfer` are not handled. |
| `keep_alive` | Correctly excluded | Per-connection | **OK** (probe confirms both legs answer their own). |

**The important per-connection bug is not the teleport ID; it is the absolute pose.** The cache stores the backend's `position` frames. After the attaching client moves, the backend updates its player position but does not send a new `position`; the proxy has no record of the movement. Probe `position-reattach-probe.mjs`:

```
backendSawPositions: [[2.5, 1.62, 2.5]]
cacheDuringDetach:   [login, game_state_change, position, chunk_batch_start, map_chunk, chunk_batch_finished]
c2Positions:         [{ id: 1, x: 0.5, y: 1.62, z: 0.5 }]
```

The runbook's test avoids this by calling `backend.sendPosition({x: 8.5, ...})` while detached (`src/scenario.js:127`), i.e. it creates the "current position" with a *backend teleport*, not with the client's actual last movement. That is a test contrivance hiding the gap. The architecture's attach sequence explicitly says "Synchronize position to the puppet's exact pose", and the research says the client should land "exactly where the puppet is". The implementation does not.

**Secondary per-connection issues:**
- The proxy replays the backend's teleport IDs verbatim (`position.teleportId` 1, 2). At 775 the client sends only `teleport_confirm` (verified against `minecraft-data`: no `accept_teleportation` serverbound packet), and the proxy drops it. So the backend is safe today. But the architecture says "proxy owns IDs"; the spike does not.
- The client's `chunk_batch_received` is dropped, so the front leg never paces batches. A vanilla client is tolerant of a server that sends multiple batches, but the architecture says "one batch in flight" and "pace on the client's acks"; the spike does not implement that.
- Chat is the clear invalid replay: `player_chat` carries a contiguous `globalIndex` and a signature-cache chain. A new client that receives a cached `player_chat` with index 99 and `previousMessages` referencing messages it never saw can fail validation or disconnect. The probe confirms the frame is cached; the code has no chat filter (`src/proxy.js:158-171`).

## 4. Does the test accidentally create a second backend login, reuse a single client, or hide a failure via error swallowing?

**Second backend login: no.** Probe counts at the fake backend's TCP server: `connections = 1`, `logins = 1`, `playerJoins = 1` across two attaches and 9.5 s detached. The scenario's independent `backend.received.logins` also stays 1. The proxy has no reconnect path, so this is structurally guaranteed; the probe confirms it at the socket level.

**Single client reuse: no.** `client1` is closed before `client2` is created; both are distinct `mc.createClient` instances (`src/scenario.js:75,131`). The same backend leg is intentionally reused. There is no overlapping-attach test; if a third client attaches while `client2` is attached, `attached` is overwritten and the old client is silently orphaned (it remains connected but its serverbound packets are dropped). That is an untested invariant violation.

**Error swallowing: yes, in ways that matter.**
- `createFakeClient` logs `clientError` to `logStream` (`src/fake-client.js:27`); the scenario/test pass `logStream: null` (`src/scenario.js:75,131`, `test/gate-a.test.js:10`). Client errors are discarded.
- `received.ended` is recorded (`src/fake-client.js:18,28-31`) but **never asserted**. A kick after `ready()` sets `ended` and nothing fails.
- The proxy's `backendError`, `frontClientError`, `frontServerError`, `backendEnd` are logged to the same null stream; the report contains no error field.
- `waitFor`/`waitUntil` swallow predicate exceptions (`src/fake-client.js:47`, `src/scenario.js:37`): a typo becomes a timeout, not a clear error. Not a silent pass, but poor diagnostics.
- The `finally` close functions swallow errors (`src/scenario.js:159-161`), and `proxy.close()`/`backend.close()` swallow (`src/proxy.js:173-179`, `src/fake-backend.js:134-139`). That is acceptable cleanup, but it means shutdown failures are invisible.
- `src/gate-a.js` has no `try/catch`: if `runGateAScenario` throws (e.g., a `waitUntil` timeout), no report is written and the CLI exits with an unhandled rejection. The docs say the report is always produced; it isn't on a throw.
- Latent race: `client2.ready()` resolves on `login + position + map_chunk` (`src/fake-client.js:55-58`), but the test immediately checks `client2.received.blockChanges` and `positions.at(-1)` (`src/scenario.js:135-142`), which are replayed **after** `chunk_batch_finished`. Five runs passed, but a slower scheduler could see `.at(-1)` as the initial `0.5` and fail. It should wait for the specific frames.
- `detachTotal === 1` is sampled after `finally` closes client 2 (`src/scenario.js:118,158-172`). Closing client 2 emits a detach; the report snapshot happens synchronously before the `end` event today, but this is a shutdown-timing dependency. If it fires earlier, the test's `assert.equal(metrics.detachTotal, 1)` fails.

**Verdict on Q4:** No second login, no client reuse, but the harness does hide post-join failures and shutdown/protocol errors.

## 5. Strongest falsification / missing negative tests

### Strongest falsification

**`position-reattach-probe.mjs`:** move to `2.5`, detach, reattach → `0.5`. This directly falsifies the architecture's L2 invariant 5 ("A second attach receives current state, not a stale replay") and the runbook's heading "Reattach sees current state". The test passes only because it injects a backend `sendPosition(8.5)` while detached. This is an implementation bug, not just a missing assertion.

The **strongest external falsifier** remains the one the runbook names: an official 26.1 vanilla client that must leave "Loading terrain…", render the chunk, stay 60 s, and break a block. This harness cannot substitute for it; both peers are `minecraft-protocol`.

### Three concrete additions, ordered by value

1. **Move → detach → reattach position regression (highest value; fails today).**
   - `client1.sendPosition(2.5)`, wait for the backend to receive it, close `client1` **without** `backend.sendPosition`, attach `client2`, wait for its `position`, assert `client2`'s last position is `2.5` (within a small epsilon) and `teleportId` is proxy-owned.
   - Fix: track the latest serverbound `position`/`position_look`/`look` per attached client in the proxy, and on attach synthesize a fresh `position` from that pose; fall back to the last backend teleport only if no serverbound pose exists. Keep the backend's teleport IDs out of the front leg.
   - This turns the runbook's claim 4 from "backend state changes are replayed" into "the puppet's current pose is reconstructed", which is what the product promises.

2. **Liveness + detach soak (highest value for the gate's core claim).**
   - After each attach, hold for ≥60 s (CI can use 10 s), assert `client.received.ended === null`, no `clientError`, `proxy.attachedClient` is non-null, `proxy.backend.state === 'play'`, and at least two keep-alive round-trips on each leg.
   - Detach and hold for ≥60 s (or the architecture's 5 min) while the backend keeps sending; assert the backend never reconnects, `backendLogins`/TCP connection count stay 1, the backend answers its keep-alives, and the cache keeps filling.
   - Add a deliberate kick: have the backend send `kick_disconnect` or destroy the socket, and assert the front client is closed with a clear reason rather than left as a zombie.
   - This closes the "a kick right after the join passes" hole and the 1-second "detach survival" claim.

3. **Adversarial per-leg ownership + clientbound-state negative suite.**
   - Instrument the fake backend to count `teleport_confirm`, `chunk_batch_received`, `keep_alive`, `cookie_response`, `resource_pack_receive`, `pong`, and every chat variant.
   - Have the fake client deliberately send all of them; assert the backend sees **only** the proxy's values (e.g., confirm IDs from the backend's teleports, ack `32`), never the client's sentinel values (777/1/424242).
   - Have the backend send `player_chat` while detached, plus `cookie_request`, `add_resource_pack`, and `ping`; assert `player_chat` is **not** replayed (or its index is rewritten), the client's `cookie_response` is swallowed, and the resource-pack/ping responses do not reach the backend.
   - Optionally tap the wire (my `/tmp/opencode/wire-tap.mjs`) and assert the exact clientbound play sequence, not just `includes`.

Secondary additions: assert `backend.received.positions.length === 1` (exactly once), assert `chunkBatchAcks >= 1`, assert `client1`/`client2` profiles, assert `map_chunk` `(0,0)` and grass content, and assert the join order.

## 7. Verdict, specifically

**As the runbook's protocol-level Gate A: PASS WITH CAVEATS.**
What is genuinely proven:
- A real two-leg proxy terminates login/config per leg and relays play frames decoded/re-framed/re-compressed.
- The cached join is replayed raw, in order, at 775: `login(entityId=42)`, `game_state_change(13)`, `position`, `chunk_batch_start`, `map_chunk(0,0)`, `chunk_batch_finished`; the chunk contains the expected grass block.
- Two sequential attaches do not create a second backend login (TCP-level probe: 1 connection, 1 login, 1 player join).
- The backend leg survives detach at the library level for ~10 s: answers keep-alives, confirms teleports `[1,2]`, acks the chunk batch `[32]`, stays in `play`.
- The front leg answers its own keep-alives; the front client's keep-alive responses never reach the backend.
- Serverbound `position`/`block_dig`/`block_place` reach the backend; serverbound `chat_message` is blocked; forced `teleport_confirm`/`chunk_batch_received`/`keep_alive` are dropped.
- Backend-originated `block_change` and `position` sent while detached are replayed to the next client.

What is not proven / false:
- The reattach does **not** land on the puppet's actual pose after the client moved (probe: `2.5` → `0.5`).
- A client that is kicked immediately after the join still passes the test (no `ended`/error assertion, null logs, no soak).
- Clientbound chat is **replayed**, not blocked; a real backend's chat can invalidate the next client's index chain.
- The cache is unbounded before `chunk_batch_finished` (2002 frames in the probe).
- Per-leg keep-alive/teleport/chunk-ack ownership is correct but unasserted.
- "Exactly once" serverbound delivery is not asserted.
- No encryption, no online-mode/`hasJoined`, no config replay, no official client, no 5-minute detach, no chunk neighbors/entities/inventory, no cache eviction, no concurrent/early attach, no backend-drop recovery.

**As the architecture's Gate A / L2: FAIL (not yet met).** The architecture's Gate A requires an official client, an online-mode front leg with `hasJoined`, a real backend, a 5-minute detach observation, and "current state, not a stale replay". The runbook deliberately scopes down to a protocol-level spike; that is a reasonable engineering choice, but it should not be recorded as "Gate A" without the caveat that it is a *subset*, not the gate.

**P1-8. Fix the real-client Gate A story and the config/encryption caveats.**
The front leg's config is generated by `mc.createServer` from `minecraft-data`, not replayed from the backend; swapping in the real backend will **not** make the front config the backend's. Add a config cache/replay or state explicitly that the real-client Gate A still needs it. Also explicitly list encryption as untested (both legs offline) and note that the architecture's L2 invariant 1 is unmet.

**P1-9. Assert "exactly once" and chunk contents.**
Change `.some(...)` to count assertions (`positions.length === 1`, `digs.length === 1`, `places.length === 1`) or count per client send. Assert `map_chunk` `x=0,z=0` and grass at `(0,0,0)` (the probe shows how), and assert the join order, not just membership.

**P1-10. Test early/concurrent attach and backend drop.**
Attach before `chunk_batch_finished` (partial prefix), attach a second client while one is attached (the proxy overwrites `attached` and orphans the first), and drop the backend (the proxy leaves the front client as a zombie because only `end` clears `attached`). These are the failure modes the architecture's T4/T5 and failure-injection sections call for.

### P2 — polish, races, wording

**P2-11. Replace weak/self-count assertions.** `framesReplayed > 0`, `serverboundForwarded >= 3`, `attachTotal === 2`, and `framesCached <= 528` are self-counts/vacuous. Assert the actual values or client/backend observations.

**P2-12. Remove the shutdown/attach races.** Wait for `client2.received.blockChanges` and the second position before checking (not just `ready()`); avoid `detachTotal` depending on the `finally` close timing; consider a `try/catch` in `gate-a.js` so a thrown scenario still writes a failure report.

**P2-13. Record errors in the report.** `logStream: null` discards `clientError`/`backendError`; add an `errors` array to the fake client/backend/proxy report and assert it is empty. Assert `received.ended === null` for both clients.

**P2-14. Harness fidelity nits.** The forged Login Success has `properties: []` (no skin; the architecture says skin properties); the fake backend does not record the backend username (assert `Puppet`); only `client1`'s profile is checked; keep-alive IDs serialize as `0` in this harness (i64/Number), so ID remapping is unproven; `testdata` report ports/timestamps are non-deterministic.

**P2-15. Handle terminal/state-change frames the cache currently replays.** `start_configuration` (mid-play config), `transfer`, `respawn`/dimension changes, `kick_disconnect`, `add/remove_resource_pack`, `cookie_request`, and `ping` are cached raw; the architecture has explicit rules for most of them. At minimum, drop or handle them and document the behavior; the cache is not a valid full replay for these.

**P2-16. Robustness of `writeRaw`/buffer lifetime.** The cache stores the `raw` event's `Buffer` reference; copy it if the library ever reuses buffers. `backend.writeRaw`/`client.writeRaw` can throw if the other leg is gone; catch and detach rather than crashing the process. `attached` is cleared only on `end`, not `error`; a front-client error can leave a dead `attached` target.
